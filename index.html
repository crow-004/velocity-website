A stolen key shouldn't stay a liability

Signing keys inside a TEE/HSM setup rotate themselves automatically, in microseconds — so a leaked or stolen key is stale before it's worth using, without slowing down signing.

The exposure window

Today, a signing key lives until someone manually notices a breach and rotates it — hours, sometimes weeks. Every minute it stays valid, a stolen key is still a fully usable liability for an attacker.

Why rotating more often isn't done today

Interactive HSM key rotation means a real network round trip — our own measured, best-case number (same-VPC, real AWS CloudHSM) is ~120ms, and that's the fast case. Too slow to do continuously on high-throughput signing infrastructure. Teams are forced to choose between frequent rotation and performance.

Where this shows up

Hot/warm wallet signing infrastructure, custody platforms, exchange withdrawal signing, payment/settlement message signing, crypto trading bots that sign every order (API keys or on-chain transactions), and any infrastructure — crypto or traditional finance — where a single compromised key can move real funds.

How it works

Autonomous key ratcheting — the mechanism, in three steps.

1

Bootstrap

TEE ↔ HSM run one ECDHE handshake and mutual attestation. Agree on K₀. One-time cost: ~0.3-0.5ms.

2

Session-key ratchet

Each side independently derives session key Kn+1 = HKDF-SHA256(Kn, salt=hardware measurement, info=counter). No network call.

3

Verify & rotate

Sliding-window replay protection + signed batch proofs make rollback attacks detectable. Measured: ~3µs/step.

Analogy

A self-reloading keycard, good for a set number of uses — the signer works at full speed without checking back with the vault each time. If tampered with, it instantly deactivates. Velocity does this for cryptographic signing keys.

What doesn't change

We don't replace the HSM — it stays the root of trust, generating the master seed and never releasing it. We remove it from the hot path, not from the trust model. Patent-pending: the subject of the USPTO provisional filing (priority date 2026-07-13) is exactly this independent-derivation mechanism.

Why it matters for you

Exchanges, custodians & payment processors

Hot/warm wallet withdrawal signing, or payment and settlement message signing, is the highest-value attack surface you operate. Automatic, hardware-backed key rotation shrinks what any single compromised signing key is worth — without adding latency.

Signing infrastructure providers

If you provide signing infrastructure for other companies' wallets or payment rails, key-rotation frequency is a direct sales argument to your own customers — and one you can currently only offer at a real performance cost.

Regulated / institutional custody

Auditors and institutional clients increasingly ask about key-rotation policy, not just key-storage policy. Continuous, hardware-enforced rotation is a stronger answer than a manual quarterly rotation runbook.

What we're not saying: not a claim that key rotation alone stops every attack — it shrinks the value of one specific, common failure mode (a leaked or stolen signing key) without a performance cost. Not a replacement for your HSM or your existing key-custody policy. In scope: network/software key theft — the overwhelming majority of real incidents. Out of scope: an attacker who physically defeats a device's own tamper response and extracts key material directly — no HSM or TEE vendor claims protection against that, and neither do we.

DeFi & EVM compatible

Transaction signing uses secp256k1 + Keccak256 — the same primitives EVM chains use, so every signature is natively verifiable on-chain via Ethereum's own ecrecover, no custom verifier needed.

Threshold-ECDSA — real and network-verified

The signing backend is already pluggable behind one Rust trait. Cluster mode (single CloudHSM/SoftHSM2) is the production default today.

Real multi-party signing, no single key ever exists in one place

Each party runs its own separate process, and a real 2-of-3 threshold-ECDSA ceremony has been run across three genuinely separate AWS machines, converging on one shared public key and one byte-identical signature.

Re-run across three continents to get a real number, not a guess

Stockholm, Virginia, and Singapore — signing between the two farthest parties took 4-6 seconds real wall clock, still trivial against a once-per-window amortization argument.

What's left is organizational, not technical: today's demo still has one operator behind every party — genuine trust separation needs each party under a genuinely different controlling organization, which no infrastructure test alone can demonstrate. An independent-key multisig alternative mixing HSM, YubiKey and software keys per signer remains a second, separately buildable option for a client who prefers it.
